01 · Executive Summary

執行摘要

Expo 是正確方向，但不應先把現在的靜態網站重構為獨立的 HeroUI Web App，之後才搬到 Expo。 這條路線會先把 DOM UI 改寫成 React DOM，再為 iOS／Android 重寫成 React Native，形成兩次 presentation layer 遷移。

建議直接建立 Expo Router 骨架，先把換算、禮包、預算與排期邏輯抽成純 TypeScript，再使用平台別的 UI adapter：

平台UI 實作共用部分
WebExpo Router Web + @heroui/reactDomain logic、types、repositories interface、routes、feature state、semantic design tokens
iOS／AndroidExpo Router + heroui-native + Uniwind
推薦決策 一個 Expo Router repository，共用產品核心與路由；Web 使用 HeroUI React，iOS／Android 使用 HeroUI Native，以 .web.tsx 與 .native.tsx 隔離 presentation layer。

02 · Evidence

證據邊界

本報告將不同信心層級明確分開，避免把架構建議誤當成已驗證的 runtime 事實。

本機確認 官方文件 分析推論 建議方案
  • 本機確認：現有檔案結構、DOM API、localStorage keys、global variables 與參考文件內容。
  • 官方文件：HeroUI React／Native 定位、HeroUI Native Web 限制、Expo platform-specific modules、Expo static rendering、Supabase 匿名帳號行為。
  • 分析推論：先做 HeroUI Web 會增加重寫成本；UI 雙 adapter 比強迫共用 JSX 穩定。
  • 建議方案：目標目錄、Phase Gates、storage adapter 邊界與 UI 分層。這些必須經過 Spike 才能成為最終決策。

03 · Current State

現有 App 架構盤點

目前專案不是 React 專案，也沒有可直接搬到 React Native 的 component tree。它是一個以單一 HTML 為主體的靜態 App。

面向現況遷移影響
UIindex.html 內嵌 CSS、HTML 與 JavaScript，約 942 行需重建 presentation layer
事件大量 inline onclick、getElementById、innerHTML需改為 React state 與 event handlers
儲存localStorage + lad_ prefix需抽象化 Web／Native storage
排期window.SCHEDULE 與 window.SCHEDULE_META應轉成 typed seed／repository
禮包規則window.PACK_DATA、window.OFFICIAL_TICKET_RULES應與 UI 完全分離
工程基礎無 package.json、TypeScript、React 與自動測試需建立全新 build／test pipeline

可保留的核心

  • 抽數與鑽石換算規則。
  • 官方贈券規則與禮包最佳化計算。
  • 預算、花費、排期的 domain model。
  • 「排期 → 換算 → 禮包建議 → 帶入錢包」的產品流程。
  • 現有文案、產品語言與非遊戲美術的視覺識別。
實作判斷 這次工作不是單純「換 UI Kit」，而是保留產品邏輯與資料、重建整個 presentation layer。

04 · UI Library Boundary

HeroUI 的關鍵限制

HeroUI ReactHeroUI Native
官方 repositoryheroui-inc/herouiheroui-inc/heroui-native
產品定位React Web UI libraryReact Native UI library
主套件@heroui/reactheroui-native
底層React DOM、React Aria、Tailwind CSS v4React Native、Uniwind、Reanimated、Gesture Handler
官方建議平台WebiOS／Android
Expo Web可作為 web-only renderer 進行 Spike官方目前明確表示不建議

HeroUI Native 官方 Quick Start 寫明：目前專注 iOS 與 Android，不建議用於 Expo Web；Web 開發應使用 HeroUI React。因此，「一套 HeroUI component tree 三端共用」現在不是可依賴的官方路徑。

不建議的順序 靜態 HTML → HeroUI React Web → HeroUI Native／Expo。第一次重寫得到 React DOM UI，第二次仍要重寫 React Native UI。

06 · Decision

架構方案比較

推薦

Expo 單 repo + 雙 UI adapter

Web 用 HeroUI React，Native 用 HeroUI Native。共用 domain、routes 與 feature state，允許 UI 層使用平台副檔名。

可選

一套 universal UI

如果最高優先是 JSX 共用率，就不應將 HeroUI 視為強制條件，而要重新評估 universal library 或 React Native primitives。

不推薦

先做 HeroUI Web

可當作可拋棄的 Web 視覺原型，但不應被視為 Expo／Native 遷移基礎。

決策原則

  • 以共用「產品知識」為目標，不以共用「每一行 JSX」為目標。
  • 路由、資料模型、計算規則、validation 與 repositories interface 必須共用。
  • 交互介面服從 Web 與 Native 的使用慣例，透過統一 semantic tokens 維持品牌一致性。
  • 在大規模改寫前，先用最小 Spike 驗證 HeroUI React 在 Expo Web static export 中的實際整合成本。

08 · Migration Plan

建議遷移路線

Baseline保存現況、抽 domain、建立 golden tests。
HeroUI Spike在 Web／iOS／Android 驗證最小互動集。
Feature Parity依換算、錢包、排期順序搬移。
Cloud & Community功能對等後再上 Supabase、Auth 與分享。

Phase 0A：保護現有功能

  • 保留現在正式站與 Git history 當 baseline，不原地覆蓋。
  • 將鑽石換算、贈券、禮包 optimizer、預算統計改成純 TypeScript functions。
  • 用現在的實際輸入與輸出建立 golden tests，防止 UI 遷移時改變計算結果。
  • 將 schedule.js 與 packs.js 改成 typed seed data。

Phase 0B：HeroUI 技術 Spike

在開始重寫整個 App 前，只做一組小型但有代表性的畫面：

  • Web：HeroUI React + Expo Router Web + static export。
  • Native：HeroUI Native + Uniwind + Expo Router。
  • 元件：Tabs、Input、Select、Dialog／Bottom Sheet、Card／Surface、Toast。
  • 裝置條件：中文字型、動態字體、鍵盤、safe area、dark mode。
Spike Gate expo export --platform web 必須成功；iOS 與 Android development build 必須可開啟並完成表單、彈窗與分頁流程。若 HeroUI React 與 Expo Web 整合成本過高，在這個 Gate 就切換方案，不要等全站重寫後才發現。

Phase 0C：功能對等

  1. 換算器與禮包建議。
  2. 帶入錢包、預算與記帳。
  3. 排期日曆。
  4. 儲存與 reload 行為。
  5. 內部 debug 入口與三個 Web-only 頁面。

Phase 1：Storage 與 Supabase

功能對等後，再改用 repository pattern，將本地儲存、雲端同步與匿名帳號加入。

Phase 2：社群與成長功能

建立 planning object、公開規劃頁、分享圖卡、每日 check-in 與 Cloudflare Worker 動態 OG。

09 · Storage & Identity

儲存與帳號遷移

Storage adapter

邊界WebNative雲端
使用者偏好／草稿localStorage 或 IndexedDB adapterSQLite／AsyncStorage adapter視需求同步
預算／花費Repository interface 不讓 feature 知道底層儲存方式Supabase + RLS
排期本地 cache + remote refreshSupabase banners

lad_* 一次性遷移

  1. 在原 Web domain 上偵測舊 keys。
  2. 先 parse 與 validate，不直接信任 JSON shape。
  3. 寫入本地新 schema，必要時再同步 Supabase。
  4. 寫入可重複執行的 migration marker。
  5. 保留舊 keys 一個過渡期，驗證後才提供清理。

匿名帳號的正確驗收

Supabase 官方說明，匿名使用者如果登出、清除瀏覽資料或改用另一裝置，就無法再存取原帳號。因此 Gate 不能以「清空全部 localStorage」測試匿名帳號恢復。

  • 本地 migration test：只刪除 lad_* keys，保留 auth session。
  • 完整清除 test：先把匿名帳號升級為 Google、Apple 或 Email 帳號。
  • 跨裝置 test：只對可恢復帳號進行。
  • UI 提示：匿名狀態要顯示「未備份，重裝可能遺失」。

10 · Risks

主要風險、假設與待決項

項目狀態影響處理方式
HeroUI React + Expo Web待驗證官方 HeroUI Web 文件主要覆蓋 Next.js／Vite，不是 Expo Web 專用整合最小 Spike + static export gate
HeroUI Native 成熟度持續更新，但仍是 1.0.x升級 Expo／Reanimated 時可能有相容變動鎖定已驗證版本，跟隨 changelog
雙 UI adapter已知成本部分畫面會有 Web／Native 兩份實作共用 feature controller／form schema／tokens，不重複 domain logic
日曆元件高度客製HeroUI 不會自動解決多卡池排期呈現視為產品核心 component，單獨設計與效能測試
Static OG已知限制Build 時不存在的公開規劃無法產生每頁 metadataCloudflare Worker 或成熟 server rendering
匿名資料不可恢復清瀏覽資料或重裝 App 可失去資料設定頁狀態文案 + 帳號升級

本報告使用的假設

  • HeroUI 仍是 UI 層的明確產品選擇，但不要求 Web 與 Native 使用同一套套件。
  • Web 仍是 SEO、零安裝試用與社群分享入口，不是可以凍結的次要平台。
  • iOS 與 Android 需要真正的 Native 互動體驗，不以 WebView wrapper 作為最終交付。
  • 本階段優先順序是功能對等與架構穩定，不同時加入大量新社群功能。

尚未決定

  • HeroUI React 在 Expo Web build pipeline 中的實際整合與 bundle 成本。
  • Native 本地資料是使用 SQLite、AsyncStorage，還是以 Supabase cache 為主。
  • Web 與 Native 是否保持同步上線，或 Web-first 後用 feature flags 開放 Native。
  • 原正式站如何在 Expo cutover 期間保留與 rollback。

11 · Actions

建議下一步

  1. 先修正架構文件：更新 One-Shot 技術表、Phase 0 與 Gate 1，不再將 StyleSheet.create 視為唯一 styling 方案。
  2. 建立獨立 migration branch：保留現在正式站與可 rollback 的 baseline。
  3. 先抽 domain tests：不先改畫面，先保證計算結果不會在遷移中漂移。
  4. 建立 HeroUI Spike：用一個表單、一個彈窗、一個分頁和一張結果卡驗證三平台。
  5. Gate 通過後才開始 feature parity：換算 → 錢包 → 排期 → storage。
  6. 將 Supabase 與社群功能留到架構對等後：避免一次調試五種變動。

12 · Handoff

給下一位 Agent 的驗證清單

  • 確認專案根目錄與作業 branch，不覆蓋現在正式站。
  • 確認 HeroUI 實際指的是 Web @heroui/react、Native heroui-native 雙 renderer。
  • 使用實際安裝版本的官方文件，不盲目複製舊版本 setup。
  • 確認 Expo Web static export 能包含 HeroUI React styles，且 hydration 無錯。
  • 確認 HeroUI Native 在 iOS／Android development build 的 Input、Select、Dialog、Bottom Sheet 行為。
  • 確認所有計算規則都在 domain/ 且不依賴 React、DOM 或 React Native。
  • 用現有 App 的輸入與結果建立 regression tests。
  • 確認 lad_* migration 是 idempotent，且不會刪除 Supabase auth session。
  • 確認 Web-only debug 頁面不會意外出現在 Native 一般導覽。
  • 在加入 Supabase／Auth 前，先完成「設預算 → 記帳 → 換算 → 禮包建議 → 帶入錢包」三端驗收。
