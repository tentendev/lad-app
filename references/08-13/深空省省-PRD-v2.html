01 / 現況拆解它其實是偽裝成遊戲工具的理財 App

《戀與深空》玩家真正的痛點不是「不知道要抽什麼」，而是「不知道自己還能花多少、什麼時候該存」。現有的三個 tab 不是三個獨立功能，而是一條完整的翻譯鏈。

外部事件
排期
卡池什麼時候開、開什麼。玩家無法控制的時間軸。
目標翻譯
換算
「我想抽到」變成「還缺幾鑽」。
代價翻譯
禮包試算
資源缺口變成新台幣，並找出最省的階級。
行為校正
錢包
記錄真實花費，回頭修正下次的預算判斷。
「帶入錢包記帳」這顆按鈕是整個產品的接合處。同類工具通常把試算和記帳分開，所以玩家算完就關掉了。把兩者焊在一起，是這個產品最被低估的設計決策，也是留存的槓桿點。

已經做對的三件事

「預留資源（抽）」這個欄位。它承認玩家的決策是跨卡池的，不是單次的。這一個欄位就把產品從計算器升級成規劃工具——它在問「這次抽完之後你還活得下去嗎」。

「提醒門檻 %」是一個 commitment device。它把課金焦慮外化成一個可控的數字。這是產品的情緒價值，比計算精度更重要，而情緒價值才是玩家回來的理由。

排期的免責聲明寫得很清楚——哪些是官方公告、哪些是預測，一句話交代完。在這個品類裡，誠實是可累積的信任資產。改版時絕對不能弄掉它，只能讓它更精確。

一個結構性弱點

排期資料目前是人工維護、寫死在前端的。這在單機工具階段完全沒問題，但一旦有了公開規劃頁，它會立刻變成整個系統的瓶頸。第 09 節專門處理這件事。

02 / 為什麼要會員登入不是為了「能記錄」

現在不用登入就已經能記錄了——localStorage 做得到。所以會員系統的價值不在儲存，而在下面四種動機之一，而它們指向完全不同的架構規模：

真實動機最小實作成本
換手機、清快取不遺失資料匿名帳號 + 雲端備份低
跨裝置同步（手機算、電腦看）正式 auth + 同步衝突處理中
拿到留存與行為數據auth + analytics + 資料治理中
做社群、做付費完整後端 + 內容維運高

本文件採用的答案是：以「跨裝置同步 + 公開分享」為目的，但用匿名優先的方式實作。也就是說，帳號存在，但它不站在使用者和價值之間。

三個必須避開的陷阱

一、登入牆放太前面會殺掉流量。這種工具必須在十秒內展示完價值。強制註冊會在漏斗最上層砍掉大半的人，而這些人正是分享圖卡帶進來的新流量。

二、課金金額是這個品類最敏感的資料。玩家很在意「我一個月在乙女遊戲花八千」被看見。這會決定隱私預設值、分享圖卡的欄位、以及所有相關文案。

三、開了登入就等於開了維運。會員系統會立刻讓排期資料的維護方式變得不可持續，然後你會被迫開一個沒排進計畫的第二專案。這份文件把它排進來了。

03 / 決策與否決鎖定的九件事，與被砍掉的兩件事

成功定義
三個月後有一群玩家每天在用。社群型工具，營收不是這一輪的目標。
社群單位
結構化的「抽卡規劃」物件。全網只有這個 App 能產生它，這是唯一有機會贏的分享單位。
社群架構
站外分享圖卡 + 站內公開規劃頁。借用 Threads／小紅書／Discord 的既有網路效應做分發，自己保持在工具定位。
留存引擎
每日存鑽進度打卡。分享負責獲取，打卡負責留存。不硬追整體日活，看的是卡池前三天的活躍尖峰。
排期資料
Supabase table + 極簡內部後台。每個卡池有穩定 ID、狀態標記、來源連結。
認證
匿名優先。開場就給匿名 session，只在要分享或要跨裝置同步時升級為正式帳號。
隱私
金額預設不公開。分享卡顯示抽數、目標卡池、進度，不顯示新台幣。想公開的人自己開開關。
平台順序
Web → Android → iOS。Web 是分享圖卡的落地頁，沒得選；iOS 延後到有用戶量再處理 IP 風險。
框架
Expo SDK + Expo Router，單一 codebase，web 使用 output: "static"。
已否決
站內曬單牆 — 玩家已經在 Threads、小紅書、巴哈、Discord 曬抽卡結果，那些地方的觀眾多兩個數量級。做站內曬單等於拿自己的冷啟動去挑戰別人的既有網路效應。
已否決
站內 feed、追蹤、留言 — 空的 feed 比沒有 feed 更傷。而且使用者上傳遊戲截圖會把 IP 風險從「工具 App」升級成「UGC 平台」，讓 iOS 上架難度再上一階。留在 Phase 4 之後重新評估。
為什麼「規劃」贏得過「曬單」

「我有 12,400 鑽，目標 80 抽，預算 NT$3,000，鎖定 9/12 生日池，另外預留 30 抽給後面的混池」——這個物件在 Threads 上不存在，因為沒有人有工具產生它。它可被討論、可被抄、可被比較、可被反駁。這是內容，不是截圖。

04 / 規劃物件可分享的最小單位長什麼樣

整個 v2 的產品核心是把散在三個 tab 裡的計算狀態，收斂成一個有名字、有 URL、可以被別人看見的物件。它必須同時滿足三件事：對自己有用（追蹤進度）、對別人有用（可讀懂並抄走）、對系統有用（長期穩定）。

欄位規格

欄位說明公開頁
標題玩家自訂，預設自動生成如「沈星回生日池 80 抽計畫」顯示
目標卡池指向 banners.id，帶卡池類型與日期顯示
目標抽數整數顯示
起始持有鑽石建立規劃時的快照，用來算進度百分比顯示
目前持有鑽石隨打卡更新顯示
金券張數原本剩餘金券 + 官方金券自動換算顯示
預留抽數為後續排期保留，不計入本次目標顯示
預算上限（NT$）這個規劃願意花的錢預設隱藏
推薦禮包階級依缺口自動算出的最省階級預設隱藏
進度快照缺口鑽數、需課金抽數、目標後剩餘鑽顯示
公開設定is_public、show_amount 兩個獨立開關—
關鍵設計約束

規劃物件必須三個月後還打得開。玩家把連結貼到 Threads，三週後有人點進來，看到的必須是一個完整、有意義的頁面——即使那個卡池已經結束。這意味著卡池不能只是前端陣列裡的一個物件，而必須是資料庫裡有穩定 ID 的一筆資料；也意味著規劃頁要處理「已結束卡池」的狀態呈現，而不是壞掉。

分享圖卡的視覺規格

圖卡是成長引擎的第一個接觸點，它在 Threads 或小紅書的資訊流裡必須一眼看懂、且不需要看文字說明就知道這是什麼。規格：

  • 尺寸：1200 × 630（OG 標準），同時輸出 1080 × 1080 供 IG 使用
  • 主視覺：一條存鑽進度條，加上「距離目標還差 N 天」的推算——這是最有情緒張力的一個數字
  • 次要資訊：目標卡池名稱與日期、目標抽數、預留抽數
  • 不出現：新台幣金額、玩家 UID、遊戲角色立繪或任何遊戲美術資產
  • 品牌：右下角「深空省省 · 你的抽卡規劃」＋短網址，字級小但可讀

不放遊戲美術是一條硬規則。它同時解決 IP 風險和圖卡辨識度兩個問題——一張純資訊設計的卡片在資訊流裡反而比又一張角色圖更醒目。

05 / 使用者旅程三條必須跑得順的路

旅程 A · 從分享圖卡進來的陌生人

這是成長迴圈的閉合處，也是最不能出錯的一條。

  1. 在 Threads 看到一張規劃圖卡，覺得「這個人算得好清楚」，點進 /p/xxxxx
  2. 看到完整的公開規劃頁：進度條、目標卡池、缺口、預留策略。沒有登入牆、沒有彈窗、沒有 App 下載提示。
  3. 頁面底部一顆主要動作：「用這個規劃當範本」——不是「註冊」，也不是「下載 App」
  4. 點下去，系統靜默建立匿名 session，把這份規劃複製成他自己的草稿，直接進入換算畫面，欄位已預填
  5. 他改成自己的數字，得到自己的結果。到這一步為止，他完全沒有註冊過。
  6. 他想存下來或分享，這時才出現升級提示（見第 08 節）
這條路的失敗模式

如果第 2 步或第 4 步出現任何形式的註冊要求，整個成長引擎就死了。分享帶來的流量是最脆弱的流量——他們對這個產品的投入是零，任何摩擦都會讓他們直接關掉。

旅程 B · 每日存鑽打卡

留存引擎。它必須能在十秒內完成，而且每次完成都要有一個微小的進展感。

  1. App 開場落在「我的規劃」，最上面是進度條和一個大按鈕：「今天領了多少鑽」
  2. 輸入數字（提供常見值快選：60、90、120、300）→ 送出
  3. 進度條前進，下方文案更新：「還差 3,200 鑽 · 照這個速度還要 18 天 · 卡池還有 22 天」
  4. 如果推算結果是「來不及」，這裡出現一行溫和的提示：「差 1,400 鑽，最省的補法是 NT$490 那階」——連到禮包試算，帶入現有數字
  5. 連續打卡的天數顯示在旁邊，但不做斷簽懲罰、不做連勝獎勵（見下方說明）
為什麼不做連勝獎勵

這個 App 的存在目的是幫玩家控制課金，不是增加他的心理負擔。連勝機制會製造「不能斷」的壓力，而斷簽的挫敗感會直接把人推走。顯示天數是資訊，設計獎勵是操縱——後者跟產品的價值主張互相矛盾。

旅程 C · 新卡池公告，重新規劃

  1. 官方公告新卡池 → 內部後台更新該筆 banner 的 status 從 predicted 變 official，補上日期與 source_url
  2. Android 收到推播（Web 用站內橫幅）：「9/12 沈星回生日池已官方公告，你的規劃需要調整」
  3. 玩家點進來，看到現有規劃旁邊出現一個對比：原本的預測日期 vs 官方日期，以及這個差異對他的存鑽節奏意味著什麼
  4. 一顆按鈕：「以官方日期重算」

這條旅程是排期資料進資料庫之後才可能存在的功能，也是它最直接的投資回報。

06 / 資料模型Supabase schema

八張表。設計原則：所有使用者資料以 owner_id 為 RLS 的唯一依據；banners 是唯一的全域共享內容表；規劃的計算結果做快照存 jsonb，讓公開頁不必在讀取時重算。

RLS policies

Supabase 的匿名 session 也是一個真實的 auth.uid()，所以 RLS 不需要為匿名使用者做特例。唯一的特例是公開規劃頁——它用 anon role 讀取，且只能讀到 is_public = true 的規劃。

supabase/migrations/0002_rls.sql
alter table profiles  enable row level security;
alter table plans     enable row level security;
alter table checkins  enable row level security;
alter table expenses  enable row level security;
alter table budgets   enable row level security;
alter table banners   enable row level security;
alter table packages  enable row level security;

-- 使用者只碰自己的資料
create policy own_profile on profiles
  for all using (id = auth.uid()) with check (id = auth.uid());

create policy own_plans on plans
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy own_checkins on checkins
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy own_expenses on expenses
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

create policy own_budgets on budgets
  for all using (owner_id = auth.uid()) with check (owner_id = auth.uid());

-- 公開規劃頁：任何人可讀，但只有公開的
create policy public_plans_read on plans
  for select to anon
  using (is_public = true);

-- 排期與禮包：所有人可讀，只有 admin 可寫
create policy banners_read on banners
  for select to anon, authenticated using (true);

create policy banners_write on banners
  for all to authenticated
  using (exists (select 1 from admin_users where user_id = auth.uid()))
  with check (exists (select 1 from admin_users where user_id = auth.uid()));

create policy packages_read on packages
  for select to anon, authenticated using (true);

create policy packages_write on packages
  for all to authenticated
  using (exists (select 1 from admin_users where user_id = auth.uid()))
  with check (exists (select 1 from admin_users where user_id = auth.uid()));
公開規劃頁的資料洩漏風險

public_plans_read 這條 policy 會讓 anon 讀到整列，包含 budget_twd 和 owner_id。RLS 是列級的，不是欄級的。正確做法是建一個 view 只曝露安全欄位，公開頁只讀 view，不直接讀 plans：

supabase/migrations/0003_public_view.sql
create view public_plans
with (security_invoker = true) as
select
  p.short_id,
  p.title,
  p.banner_id,
  p.start_diamonds,
  p.current_diamonds,
  p.target_pulls,
  p.gold_tickets,
  p.reserved_pulls,
  p.computed,
  p.view_count,
  p.updated_at,
  case when p.show_amount then p.budget_twd else null end as budget_twd,
  pr.display_name,
  pr.avatar_emoji
from plans p

07 / 分享圖卡架構Expo 靜態輸出解不掉的那一題

這是整個技術方案裡唯一真正棘手的地方，值得單獨一節。

問題

Expo Router 的 web 靜態輸出是在 build 時把每個路由渲染成 HTML。但公開規劃頁是使用者生成的——build 的時候那些規劃還不存在。這代表 /p/[短碼] 拿不到正確的 og:image 和 og:title，而整個成長引擎完全依賴這兩個 tag 在 Threads 和小紅書上正確展開。

方案：Cloudflare Worker 前置攔截

不為了這一條路徑多養一套 Next.js。用一個 Worker 攔 /p/*，依請求者身分分流：

Step 1
Worker 攔截
/p/:shortId 進入 Worker，不落到靜態資源。
Step 2
讀 view
用 anon key 查 public_plans，KV 快取 5 分鐘。
Step 3
分流
爬蟲 UA 拿純 meta HTML；真人拿含 meta 的 shell，再 hydrate 進 Expo web。
Step 4
圖卡
Satori + resvg 在 Worker 生成 PNG，寫入 R2，之後直接由 R2 供應。
圖卡的 cache key 用 shortId + updated_at，規劃一更新就自然失效重生，不需要手動清快取。R2 已經在 s4.tenten.co 上，不用開新服務。
workers/share/src/index.ts — 骨架
const BOT_UA = /(facebookexternalhit|Twitterbot|threadsbot|Discordbot|
Slackbot|WhatsApp|LinkedInBot|TelegramBot|bingbot|Googlebot|
xiaohongshu|Line)/i;

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const url = new URL(req.url);

    // 圖卡：/og/:shortId.png
    const og = url.pathname.match(/^\/og\/([A-Za-z0-9_-]{6,12})\.png$/);
    if (og) return renderCard(og[1], env);

    // 公開規劃頁：/p/:shortId
    const pg = url.pathname.match(/^\/p\/([A-Za-z0-9_-]{6,12})$/);
    if (!pg) return env.ASSETS.fetch(req);

    const plan = await getPlan(pg[1], env);       // KV 快取 300s
    if (!plan) return notFound(env);

    const meta = buildMetaTags(plan, url.origin); // og:title / og:image / description
    const isBot = BOT_UA.test(req.headers.get('user-agent') ?? '');

    if (isBot) return html(metaOnlyDocument(meta));

    // 真人：注入 meta 到 Expo 靜態 shell，前端自行 fetch 完整資料
    const shell = await env.ASSETS.fetch(new Request(url.origin + '/p/[shortId].html'));
    return html((await shell.text()).replace('<!--META-->', meta));
  }
};
為什麼不用 Expo 的 SSR

Expo Router 的 streaming SSR 在 SDK 55+ 還是 alpha 階段。成長引擎不應該建在 alpha 功能上。Worker 這個方案多寫大約 150 行程式，但它是完全可預測的，而且落在既有的 Cloudflare 基礎設施裡。等 SSR 穩定了再把 Worker 拆掉，成本很低。

08 / 認證與升級帳號存在，但不站在使用者前面

Supabase 的匿名登入會發一個真實的 auth.users 列和 JWT，之後可以用 updateUser 掛上 email 或 OAuth identity，而且 user.id 不會變。這代表所有既有資料自動延續，不需要搬移。這是整個匿名優先策略成立的技術基礎。

時序

時機行為
App 首次啟動靜默呼叫 signInAnonymously()，不顯示任何 UI。從此所有讀寫都走 RLS，跟正式帳號完全一樣的程式路徑。
使用者按「公開這份規劃」第一次出現升級提示。理由文案：「公開規劃需要一個帳號，這樣別人看到的時候你才能改它。」
使用者按「在其他裝置繼續」同上，但理由換成同步。
連續打卡達 7 天出現一次性的溫和提示：「你的紀錄目前只存在這台裝置上」，附一顆「建立備份」。可關閉，且不再出現第二次。
其他所有時候不提。

Provider 選擇

  • Google — 三平台都可用，Android 上摩擦最低
  • Apple — iOS 上架時是強制的（有第三方登入就必須提供 Sign in with Apple），先接好省得日後回頭改
  • Email magic link — 保底選項，不需要記密碼，也照顧不想綁社群帳號的玩家
LINE Login 的判斷

台灣受眾第一反應會想加 LINE Login。Phase 2 先不加。理由：它需要獨立的 provider 設定與審核、在 Expo 上需要額外的 native 設定、而 Google + Apple 已經覆蓋幾乎所有裝置。等 Android 上架後看實際轉換率數據，如果 email magic link 的使用率異常高，那才是加 LINE 的訊號。

必須處理的邊緣情況

匿名 session 遺失。使用者清瀏覽器資料或重裝 App，匿名帳號就永久消失了，資料無法救回。這個事實必須在 UI 上誠實呈現（設定頁一行狀態文字：「未備份 · 資料只存在這台裝置」），而不是等出事才解釋。

升級時撞到既有帳號。使用者的匿名帳號要掛上一個已經被別的帳號用過的 Google identity 時，Supabase 會回錯誤。這時要給明確選擇：登入既有帳號（放棄這台裝置上的匿名資料，但先顯示會失去什麼），或改用其他 provider。不要靜默合併資料——兩份規劃合併沒有正確答案。

09 / 排期維運後台把最大的維運負擔壓到半天工

這一節解決第 01 節提到的結構性弱點。目標不是做一個漂亮的 CMS，是把「更新一筆排期」從十五分鐘（改 code、commit、等 deploy）壓到三十秒（填表、送出）。

範圍

  • 單一路由 /admin/banners，用 admin_users 白名單控制，非白名單直接 404
  • 一張表格，可新增、編輯、刪除 banner，欄位就是 banners 那幾個
  • status 用三顆按鈕切換（官方 / 預測 / 爆料），改成 official 時強制要求填 source_url
  • ID 由 start_date + 角色 slug + pool_type 自動生成，但可手動覆寫（因為它是永久 URL 的一部分）
  • 存檔後自動 purge Cloudflare KV 中相關的規劃頁快取
狀態轉換是一個產品事件，不只是資料更新

predicted → official 這個轉換要觸發旅程 C 的推播。所以後台存檔時要判斷：如果日期有變動且該卡池已被 N 份規劃引用，就把這批規劃標記為「需重算」，並排入推播佇列。這個判斷寫在一個 Postgres trigger 或 Edge Function 裡，不要寫在後台前端。

免責聲明的自動化

現有的免責聲明是手寫的，會隨時間變成謊言。改成從資料生成：排期頁底部的說明文字依當月 banner 的 status 分布自動組出來，每一筆 official 的卡池在 UI 上帶一個可點的來源連結。這讓「誠實」變成系統性質，而不是靠記得更新。

11 / 隱私設計金額是這個產品最敏感的資料

一個乙女遊戲玩家的月課金金額，是他不會主動告訴朋友的數字。整個隱私設計圍繞這一點展開，而不是圍繞法規最低要求。

決定做法
金額預設不公開show_amount 預設 false，且與 is_public 完全獨立。公開規劃 ≠ 公開金額。
公開頁走 view永不讓 anon 直接 select plans。public_plans view 在 SQL 層就把 budget_twd 依開關遮掉，前端不參與這個判斷。
顯示名稱不強制公開規劃可以完全匿名（顯示為「一位玩家」）。取名字是選項，不是條件。
金額遮蔽模式錢包頁一個切換，把所有金額顯示成 NT$•••。給在通勤時開 App 的人用。
刪除是真刪除設定頁提供「刪除所有資料」，走 auth.users 的 cascade delete。不做軟刪除。
不做 tracking不接任何廣告 SDK、不做跨 App 追蹤。這讓 iOS 的 ATT 提示完全不需要出現，也讓隱私政策可以短到一頁。

12 / IP 與上架風險最大的單點風險不是技術

非官方的第三方遊戲工具在應用商店是灰區。Apple 會用 4.1（Copycats）、5.2.1（Generally）、5.2.2（Third-Party Sites/Services）來處理這類 App，而且駁回時通常不會告訴你具體是哪一段有問題。

一個真實的參照案例

有開發者做過《魷魚遊戲》的伴看 App，刻意不使用任何 Netflix 或劇集 logo、App 描述裡完全不提節目名稱，仍然被以 Guideline 4.1 Copycats 駁回，理由是「metadata 似乎包含第三方內容」。這說明「不放 logo」是必要條件，但遠遠不是充分條件。

現在就要做的四件事

  1. 零遊戲美術資產。不放角色立繪、不放卡面、不放 UI 截圖，包含商店頁截圖。角色一律以純文字名稱出現。這條規則寫進 codebase 的 CLAUDE.md，避免日後有人「順手加個圖比較好看」。
  2. 主詞是工具，遊戲是受詞。所有對外文案的句型是「抽卡課金規劃工具，支援《戀與深空》」，不是「《戀與深空》抽卡工具」。App 名稱「深空省省」本身已經規避了直接商標，保留它。
  3. 免責聲明升級成常設頁面。不只在排期頁底部，另建一個 /about：本 App 為玩家自製工具、與遊戲營運商無隸屬關係、所有排期資料來自公開資訊或玩家推測、遊戲名稱與角色名稱之權利屬於各自所有者。這一頁在送審時是可以直接引用的材料。
  4. 資料結構為多遊戲留伸縮。banners 加一個 game_id 欄位（Phase 1 就加，值先全部填同一個）。這不是要現在做多遊戲，是讓「改定位」這條退路的成本從重構降級為填資料。
iOS 的兩條路

路線 A：等有量再送審。用戶數本身就是溝通材料，被駁回時的申訴也更有底氣。這是目前的預設。

路線 B：以通用工具定位進場。如果 iOS 的重要性比預期高（台灣年輕女性 iPhone 占比確實高），正確解法不是搶著送審，而是先接上第二個遊戲，讓 App 在事實上就是一個多遊戲工具，ASO 主打通用能力。這條路把 IP 風險從「未授權的粉絲 App」降到「支援多款遊戲的第三方工具」，是完全不同的審核情境。

15 / 開放問題需要在 Phase 2 之前有答案

  1. 預測排期出錯的信任成本要怎麼吸收？目前的免責聲明處理的是「事前告知」，但沒處理「事後修正」。如果一份被公開分享的規劃因為預測錯誤而整體失效，那個頁面該長什麼樣？建議做法是在規劃頁上明確標示「本規劃基於預測排期，已於 X 日修正」，把修正歷程當成可信度的證明而不是瑕疵。
  2. 推播的騷擾邊界在哪？「卡池前三天提醒」對認真規劃的玩家有用，但對已經決定不抽的人就是在推銷。是否需要一個「這個卡池我跳過」的動作來抑制推播？傾向要，但這會增加一個狀態。
  3. 熱門規劃牆的排序會不會製造課金競賽？依 view_count 排序可能讓「目標抽數最高」的規劃自然浮上來，變成間接鼓吹重課。是否要在排序中降權高預算規劃，或改成隨機抽樣展示？這件事跟產品的道德立場直接相關，不只是演算法選擇。
  4. 要不要做「規劃比較」？兩份規劃並排看是很自然的延伸，也很符合「規劃即內容」的方向。但它會把產品往社群推一步。建議先看熱門規劃牆的實際使用行為再決定。

這份文件的核心判斷只有一句：深空省省的護城河是「規劃」這個結構化物件，不是社群、不是排期資料、也不是計算精度。所有功能決策都應該回頭問一次，它是不是讓那個物件更好用、更可信、更值得被貼出去。
