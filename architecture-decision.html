最終結論

直接建立一個 Expo Router repository。Web 使用 @heroui/react；iOS 與 Android 使用 heroui-native + Uniwind。共用 domain、types、feature state、repository interfaces、routes 與 semantic design tokens，UI renderer 允許分平台實作。

Expo 是正確方向，但這不是把現有 HTML 包成 App，而是保留產品邏輯與資料後，以 React Native／Expo 重建 presentation layer。

原本規劃的順序：

現有 HTML → HeroUI Web 重構 → Expo

應改成：

保護現況與計算規則
→ 建立 Expo Router
→ 同時驗證 HeroUI Web / Native
→ 搬移既有功能
→ 最後加入 Supabase、會員與社群

原因是 heroui-inc/heroui 是 React DOM Web library；行動端是另一個 HeroUI Native repository。HeroUI Native 官方目前也不建議用於 Web。

不採用：先重構現有靜態網站成 HeroUI Web，再搬到 Expo。這會產生兩次 UI 重寫。

必須修正的文件衝突

  1. One-Shot 固定使用 StyleSheet.create，但 HeroUI Native 正式使用 Uniwind。
  2. Phase 0 宣稱只做功能對等，卻同時加入 Supabase、Auth 和資料庫 migrations。
  3. One-Shot 把 tabs 改成「規劃／排期／錢包」，現有功能其實是「錢包／排期／換算」。
  4. 月卡/週卡 等既有字串不能在 migration 中任意改名。
  5. 匿名 Supabase session 清除後不可恢復，不能用清空整個 localStorage 測試跨裝置恢復。

依賴原則

  • Route 只負責導航與 deep link。
  • Domain 不得依賴 React、DOM、React Native 或 Supabase。
  • Feature hooks 組合 domain、validation 與 repositories。
  • Web 與 Native renderer 可直接使用各自 HeroUI 套件。
  • 只包裝穩定的品牌元件，不為每個 Button 建立多餘 abstraction。
  • 共用 semantic tokens，例如 accent、surface、danger、spacing.md。

建議遷移順序

Gate 0：保護現況

  • 保留現有 production 與 Git history，不原地覆蓋。
  • 抽出 calculator、official tickets、package optimizer、budget totals。
  • 建立 golden tests，鎖定現有輸入輸出。
  • 將 schedule.js 和 packs.js 轉成 typed seed data。

Gate 1：HeroUI 技術 Spike

  • Web：Expo Router Web + @heroui/react + static export。
  • Native：Expo Router + heroui-native + Uniwind。
  • 驗證 Input、Select、Card、Modal／BottomSheet、Toast 與 navigation。
  • 檢查中文字型、keyboard、safe area、dynamic type、dark mode。
  • npx expo export --platform web 必須成功。

Gate 2：功能對等

  1. 換算與官方金券。
  2. 禮包 optimizer。
  3. 帶入錢包。
  4. 預算與花費 CRUD。
  5. 排期日曆。
  6. Storage 與 lad_* migration。
  7. Web-only debug 頁面。

Gate 3：Web cutover

  • 設定 web.output: "static"。
  • 確認 SEO metadata、fonts、assets 和 hydration。
  • 原網域執行一次性舊資料 migration。
  • 保留舊 deployment 作 rollback。

Gate 4：Cloud 與社群

  • Supabase repositories、RLS、匿名帳號與帳號升級。
  • 規劃物件、公開規劃頁與分享圖卡。
  • Cloudflare Worker、排期後台、打卡與推播。

主要風險

風險影響處理方式
HeroUI React + Expo Web 未實測Build、Tailwind 或 hydration 可能阻塞先做最小 Spike，通過才搬全站
HeroUI Native 仍是 1.0.xExpo／Reanimated 升級可能破壞相容性鎖定通過測試的版本並追蹤 changelog
雙 renderer部分 UI 需要兩份實作共用 domain、hooks、schema、view models 與 tokens
排期日曆高度客製效能、overflow、accessibility 容易退化視為核心元件並獨立測試
舊資料遺失使用者失去預算和消費紀錄Schema validation、idempotent marker、保留舊 keys、rollback test
匿名帳號不可恢復清除資料或重裝後失去內容明示未備份；跨裝置只驗收正式帳號
Static OG新規劃無法在 build 時產生動態 metadata後續使用 Cloudflare Worker

必須鎖定的隱性規則

  • 官方金券 milestone 使用 < target，達成目標當下拿到的券不能倒扣同一目標。
  • 預留資源不觸發官方返券。
  • 密約在日曆只佔開始日。
  • 現有日曆只有三條活動 lanes；新 UI 應顯示 +N overflow，不得靜默隱藏。
  • 「帶入錢包記帳」是核心互動，不得移除。

最終開發基準

Framework: Expo SDK 57 + Expo Router
Web UI: @heroui/react v3 + Tailwind CSS v4
Native UI: heroui-native 1.0.x + Uniwind
Shared: TypeScript domain + feature state + repositories + semantic tokens

第一個實作工作不是改寫現有 HTML，而是：

  1. 建立 migration branch。
  2. 抽出並測試 domain logic。
  3. 建立可拋棄的 Expo × HeroUI 三平台 Spike。
  4. Spike 通過後才開始正式 UI 重構。
後續架構、實作 prompt 與 Phase 規劃如與本文衝突，以本文為準。若要改變本決策，必須新增 ADR 並記錄實測證據、遷移成本與 rollback plan。
